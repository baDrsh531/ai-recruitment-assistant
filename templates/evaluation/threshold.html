Pourquoi ce seuil

F{{ calibration.beta|floatformat:0 }}

Le cout de l'erreur n'est pas symetrique. Recevoir un candidat moyen coute une heure d'entretien ; ecarter un bon candidat coute un recrutement, et le cout est supporte par quelqu'un qui n'en saura jamais rien. Le seuil retenu maximise donc un F{{ calibration.beta|floatformat:0 }}, qui pese le rappel quatre fois plus que la precision.

Ce choix est un jugement, pas un resultat. Il est expose en constante dans le code, et le tableau ci-dessous donne tous les seuils : un recruteur qui voudrait trancher autrement dispose des memes chiffres.

{% if calibration.perfectly_separable %}

a lire avec mefiance A {{ calibration.recommended_percentage }} %, le seuil separe parfaitement le jeu annote : aucun bon profil manque, aucun mauvais retenu. Mais la marge n'est que de {{ calibration.plateau_width_points }} point(s) ({{ calibration.plateau_low_percentage }}–{{ calibration.plateau_high_percentage }} %). Un resultat parfait sur une marge aussi etroite en dit autant sur la facilite du jeu annote que sur la qualite du moteur, et ne garantit rien sur des candidatures reelles. Etoffer le jeu reste le principal levier.

« Bons manques » est la colonne qui compte : ce sont des profils juges dignes d'un entretien qu'un seuil place trop haut aurait ecartes. Dans un processus reel, ce chiffre n'est jamais observable — personne ne sait ce qu'aurait donne l'entretien qui n'a pas eu lieu. C'est precisement ce que le jeu annote permet de mesurer.

Ce que ce seuil ne fait pas

Il n'ecarte aucune candidature. Le classement affiche une ligne indicative a {{ calibration.recommended_percentage }} % ; tout ce qui se trouve dessous reste consultable, scorable et recevable. Sortir un candidat du processus demande toujours un recruteur habilite et un motif ecrit.
